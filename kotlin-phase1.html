Section 01 · Kotlin Core
Visibility Modifiers
Controls who can access a class, function, or property. Each modifier explained separately with single-module and multi-module examples.
ModifierClass LevelFile / Top LevelKey Point
publicEverywhereEverywhereDefault — write nothing
privateSame class onlySame file onlyStrictest scope
protectedClass + subclasses❌ Not allowedInheritance only
internalSame Gradle moduleSame Gradle moduleUnique to Kotlin
1. public default
Definition
public is the default visibility in Kotlin. If you write no modifier, it is public. A public class, function, or property can be accessed from any class, any file, any module. Writing public explicitly is optional — most style guides omit it.
Expanding Further
In Android your Repository interfaces, ViewModel StateFlow, and ApiService interface are public because different layers of your app need them. Public = zero restriction anywhere in the project.
Single Module Example
kotlin — single module
// UserRepository.kt — public by default
class UserRepository {                      // accessible everywhere
    fun getUser(id: String): User { ... }   // public by default
}

fun formatDate(ts: Long): String = "..."   // public top-level fn

// MainActivity.kt — same module, different file
class MainActivity : AppCompatActivity() {
    val repo = UserRepository()              // ✅ public — works
    val d = formatDate(123456789L)           // ✅ public — works
}
Multi-Module Example
kotlin — :core:network module
// :core:network module — ApiService.kt
interface ApiService {                        // public — other modules need this
    @GET("users/{id}")
    suspend fun getUser(@Path("id") id: Int): User
}
kotlin — :feature:home module (consumer)
// :feature:home module — can access ApiService because it's public
class HomeViewModel @Inject constructor(
    private val api: ApiService  // ✅ public interface — accessible cross-module
) : ViewModel() { ... }
⚡ IBM Interview Q&A
Q: Do you need to write public explicitly in Kotlin?
No. public is the default. Writing it is optional. Most Kotlin style guides omit it to reduce noise, unless the team wants to make visibility intent very explicit across a large codebase.
2. private strictest
Definition
private is the strictest modifier. At class level — accessible only inside that class. Even subclasses cannot see it. At file/top level — accessible only inside that exact .kt file.
Expanding Further — Why private in ViewModel
The most important Android use of private is the MutableStateFlow / MutableLiveData pattern. Only ViewModel should mutate state. If MutableStateFlow were public, any Fragment or Composable could call .value = ... directly — bypassing ViewModel and breaking the single-source-of-truth principle.
Class Level Example
kotlin — private at class level
class LoginViewModel : ViewModel() {
    // private — only THIS class can mutate state
    private val _uiState = MutableStateFlow<LoginUiState>(LoginUiState.Idle)
    // public — anyone can observe, but NOT mutate
    val uiState: StateFlow<LoginUiState> = _uiState.asStateFlow()

    private fun validateEmail(email: String) = email.contains("@")

    fun login(email: String, pass: String) {
        if (!validateEmail(email)) return   // ✅ same class
        _uiState.value = LoginUiState.Loading    // ✅ same class
    }
}

class LoginScreen {
    val vm = LoginViewModel()
    // vm._uiState         ❌ private — compiler error
    // vm.validateEmail()  ❌ private — compiler error
    // vm.uiState          ✅ public — can observe
}
File Level Example
kotlin — private at file level
// NetworkUtils.kt
private fun buildAuthHeader(token: String) =
    mapOf("Authorization" to "Bearer $token")   // only inside NetworkUtils.kt

fun createOkHttp(token: String): OkHttpClient {
    val headers = buildAuthHeader(token)          // ✅ same file
    return OkHttpClient.Builder().addInterceptor {
        it.proceed(it.request().newBuilder().headers(Headers.of(headers)).build())
    }.build()
}

// MainActivity.kt
// buildAuthHeader("xyz")  ❌ private top-level — not accessible
⚡ IBM Interview Q&A
Q: Why private MutableStateFlow + public StateFlow in ViewModel?
Encapsulation and MVVM contract. Only ViewModel should change UI state — that is its job. Exposing MutableStateFlow lets any subscriber mutate state directly, bypassing ViewModel, breaking the single-source-of-truth principle that makes MVVM testable.
Q: What is the difference between private at class level vs file level?
Class level private: only that class body can access it — not even subclasses. File level private: the top-level declaration is visible only within that .kt file, to all code in the file regardless of class.
3. protected inheritance only
Definition
protected is accessible inside the declaring class AND all subclasses. It is NOT available at top/file level — using it there is a compile error. It exists purely for class hierarchy sharing.
Single Module Example
kotlin — single module
// BaseViewModel.kt
abstract class BaseViewModel : ViewModel() {
    // protected — subclasses share this, outside world cannot access
    protected val _loading = MutableStateFlow(false)
    val loading = _loading.asStateFlow()

    protected fun handleError(t: Throwable): String = when (t) {
        is IOException    -> "No internet"
        is HttpException  -> "Server error: ${t.code()}"
        else              -> "Something went wrong"
    }
}

// UserViewModel.kt — same module, subclass
class UserViewModel(
    private val repo: UserRepository
) : BaseViewModel() {
    fun fetchUser(id: String) {
        viewModelScope.launch {
            _loading.value = true             // ✅ protected — subclass access
            repo.getUser(id).onFailure {
                println(handleError(it))      // ✅ protected — subclass access
            }
            _loading.value = false
        }
    }
}

// HomeFragment.kt — same module, NOT a subclass
class HomeFragment : Fragment() {
    val vm: UserViewModel by viewModels()
    // vm.handleError(...)  ❌ protected — Fragment is not a subclass
    // vm.loading.collect   ✅ public StateFlow — accessible
}
Multi-Module Example
kotlin — :core:ui module (BaseFragment)
// :core:ui module
abstract class BaseFragment : Fragment() {
    protected fun showSnackbar(msg: String) {
        Snackbar.make(requireView(), msg, Snackbar.LENGTH_SHORT).show()
    }
    protected fun navigateTo(directions: NavDirections) {
        findNavController().navigate(directions)
    }
}
kotlin — :feature:home module (consumer)
// :feature:home module — HomeFragment extends BaseFragment
class HomeFragment : BaseFragment() {  // subclass — cross-module
    override fun onViewCreated(view: View, ...) {
        showSnackbar("Welcome!")           // ✅ protected — subclass access works cross-module
        navigateTo(HomeFragmentDirections.toDetail())
    }
}
⚡ IBM Interview Q&A
Q: Can protected be used at top level in a Kotlin file?
No. protected at top level is a compile error. protected only makes sense in a class hierarchy — there is no inheritance concept at file level. For file-level restriction use private or internal.
Q: Does protected work across modules in multi-module projects?
Yes. If a class in :feature:home extends a class from :core:ui, it can access protected members from the parent — even though they are in different Gradle modules. protected is about inheritance, not module boundaries.
4. internal unique to Kotlin
Definition
internal restricts access to the same Gradle module. There is no Java equivalent. Designed specifically for multi-module Android projects — hide your implementations inside a module while keeping the interface public for others to depend on.
Expanding Further
internal is the key to enforcing clean architecture at the Gradle level. You expose only interfaces publicly. Concrete implementations stay internal. Other modules cannot bypass your architecture by directly instantiating your concrete classes — the compiler prevents it.
Single Module Example
kotlin — single module
// In a single-module app, internal = same module = entire app
// Useful to hide implementation from test code or to signal intent

internal class TokenRefreshManager(
    private val prefs: SharedPreferences
) {
    internal fun refreshIfExpired() { ... }
}

// Can be used in same module freely
class AuthInterceptor @Inject constructor(
    private val tokenManager: TokenRefreshManager  // ✅ same module
) : Interceptor { ... }
Multi-Module Example — The Main Use Case
kotlin — :core:data module
// :core:data module

// PUBLIC interface — contract exposed to all modules
interface UserRepository {
    suspend fun getUser(id: String): Result<User>
    suspend fun saveUser(user: User)
}

// INTERNAL implementation — hidden from :feature, :app
internal class UserRepositoryImpl(
    private val api: ApiService,
    private val dao: UserDao
) : UserRepository {
    override suspend fun getUser(id: String) = runCatching { api.getUser(id) }
    override suspend fun saveUser(user: User) = dao.insert(user)
}

// INTERNAL Hilt module — wires interface → implementation inside :core:data
@Module
@InstallIn(SingletonComponent::class)
internal abstract class DataModule {
    @Binds @Singleton
    abstract fun bindUserRepo(impl: UserRepositoryImpl): UserRepository
}
kotlin — :feature:home module (consumer)
// :feature:home module
@HiltViewModel
class HomeViewModel @Inject constructor(
    private val repo: UserRepository  // ✅ public interface — accessible
) : ViewModel() {
    // val impl = UserRepositoryImpl(...)  ❌ internal — compile error
    // DataModule is internal — :feature cannot see the binding setup
    // But Hilt provides UserRepository via the public interface automatically
}
⚡ IBM Interview Q&A
Q: Difference between private and internal?
private restricts to the same class or same file. internal restricts to the same Gradle module — which can have hundreds of files and classes. internal is module-level encapsulation, private is class/file-level encapsulation.
Q: Why is internal important in multi-module Android?
It enforces clean architecture at compile time. You expose only interfaces publicly. Implementations stay internal. Other modules cannot bypass your architecture by instantiating your concrete classes directly. This is Gradle-level boundary enforcement — not just a convention.
Q: If I mark a class internal in :core:data, can :app module access it?
No. :app is a separate Gradle module. internal is scoped to the module it is declared in. Even if :app depends on :core:data in build.gradle, it still cannot access internal classes from :core:data — the compiler blocks it.
Section 02 · Kotlin Core
OOP Fundamentals
val/var, open/abstract/sealed, data class, object, companion object.
val vs var
Definition
val — declares a read-only property. The reference cannot be reassigned once set. However if the object it points to is mutable, its internal state can still change.
Expanding Further
val compiles to a Java final variable — the reference is fixed, not object content. var is mutable and can be reassigned any number of times. const val is evaluated at compile time, only primitives and String, must be top-level or in companion object.
kotlin
val list = mutableListOf(1, 2, 3)
list.add(4)         // ✅ internal state changed
// list = mutableListOf()  ❌ reference reassignment — compiler error

var count = 0; count = 5   // ✅ allowed

const val BASE_URL = "https://api.example.com"  // compile-time, inlined everywhere
val token = fetchToken()                         // runtime value
⚡ IBM Q&A
Q: val cannot be reassigned — how is it different from const val?
val is evaluated at runtime and can hold any object. const val is evaluated at compile time, limited to primitives and String, and the compiler inlines it at every usage site — zero runtime overhead.
open / abstract / sealed
Definition
In Kotlin all classes are final by default. These three keywords unlock different kinds of class hierarchy behavior.
kotlin — open
open class BaseFragment : Fragment() {
    open fun showLoader() = println("Showing loader")  // can override
    fun hideKeyboard() { }                              // NOT open
}
class HomeFragment : BaseFragment() {
    override fun showLoader() = println("Custom loader")
}
kotlin — abstract
abstract class BaseViewModel : ViewModel() {
    abstract fun onScreenCreated()  // must implement
    abstract fun onRetry()
    protected fun handleError(e: Throwable) = println(e.message)  // shared
}
class UserViewModel(val repo: UserRepository) : BaseViewModel() {
    override fun onScreenCreated() { fetchUser() }
    override fun onRetry() { fetchUser() }
    private fun fetchUser() { }
}
kotlin — sealed
sealed class UiState<out T> {
    object Loading : UiState<Nothing>()
    data class Success<T>(val data: T) : UiState<T>()
    data class Error(val msg: String) : UiState<Nothing>()
}
fun render(state: UiState<User>) {
    when (state) {  // no else — exhaustive
        is UiState.Loading  -> showLoader()
        is UiState.Success  -> showData(state.data)
        is UiState.Error    -> showError(state.msg)
    }
}

⚡ IBM Q&A
Q: Why are Kotlin classes final by default?
Effective Java Item 17: design and document for inheritance or prohibit it. Kotlin enforces this — accidental inheritance causes hard-to-find bugs. You must explicitly mark open to allow subclassing, making intent clear.
Q: When would you use sealed over enum?
When each case needs to carry different data. enum values are simple constants. sealed subclasses can each hold different types: Success<T> holds data, Error holds a message String. Enums cannot do this.
data class
Definition
A data class is designed to hold data. Kotlin auto-generates 5 things: equals(), hashCode(), toString(), copy(), and componentN() for destructuring.
kotlin
data class User(val id: Int, val name: String, val email: String)

val u1 = User(1, "John", "john@gmail.com")
val u2 = User(1, "John", "john@gmail.com")
u1 == u2    // true  — structural equality
u1 === u2   // false — different objects in memory
val u3 = u1.copy(name = "Jane")       // shallow copy, only name changed
val (id, name) = u1                    // destructuring via componentN()
⚡ IBM Q&A
Q: Which properties are included in equals and hashCode?
Only properties in the primary constructor. Properties declared in the class body are NOT included — a common interview trap.
Q: What is the trap with mutable var fields in data class?
Two equal objects can become unequal after mutation. copy() is shallow — nested mutable objects are shared references. Always prefer val in data classes.
object vs companion object
Definition
object declares a singleton — one instance, lazily created on first access. companion object is tied to its class and provides Kotlin's equivalent of Java static members.
kotlin
// object — standalone singleton
object AppAnalytics {
    fun log(event: String) { println(event) }
}
AppAnalytics.log("screen_open")  // no instantiation needed

// companion object — Kotlin "static"
class UserViewModel(private val repo: UserRepository) : ViewModel() {
    companion object {
        private const val TAG = "UserViewModel"
        fun factory(repo: UserRepository) = object : ViewModelProvider.Factory {
            override fun <T : ViewModel> create(cls: Class<T>): T {
                @Suppress("UNCHECKED_CAST")
                return UserViewModel(repo) as T
            }
        }
    }
}
UserViewModel.factory(repo)  // called on class, not instance
⚡ IBM Q&A
Q: JVM difference between object and companion object?
object compiles to a class with a static INSTANCE field — true lazy singleton. companion object compiles to a static nested class inside the enclosing class. Both can implement interfaces — unlike Java static methods.
Section 03 · Kotlin Core
Extension Functions
Add new functions to existing classes without modifying or inheriting from them.
What is an Extension Function?
Definition
An extension function lets you add a new function to an existing class without modifying the class or using inheritance. The class being extended is the receiver type, accessed as this inside the function.
Expanding Further — Bytecode Level
Extension functions compile to a static method with the receiver as the first parameter. They do NOT modify the class and have NO access to private or protected members — only public members.
kotlin — basic syntax
fun String.isValidEmail(): Boolean =
    this.contains("@") && this.contains(".")

fun Int.dpToPx(density: Float): Int = (this * density + 0.5f).toInt()

"user@gmail.com".isValidEmail()  // true
16.dpToPx(3.0f)                   // 48
// Compiles to: ExtensionsKt.isValidEmail("user@gmail.com")
Android Platform Extensions
kotlin
fun Context.toast(msg: String) =
    Toast.makeText(this, msg, Toast.LENGTH_SHORT).show()

fun View.show() { visibility = View.VISIBLE }
fun View.hide() { visibility = View.GONE }

fun Fragment.hideKeyboard() {
    val imm = requireContext().getSystemService(Context.INPUT_METHOD_SERVICE)
                as InputMethodManager
    imm.hideSoftInputFromWindow(view?.windowToken, 0)
}

class UserFragment : Fragment() {
    override fun onViewCreated(view: View, ...) {
        progressBar.show(); errorText.hide(); toast("Welcome!"); hideKeyboard()
    }
}
Extension Properties + Nullable Extensions
kotlin
// Extension property — computed, no backing field
val Int.dp: Float
    get() = this * Resources.getSystem().displayMetrics.density

val padding = 16.dp  // computed each access

// Extension on nullable type — safe to call without ?.
fun String?.orDefault(default: String = ""): String = this ?: default

val name: String? = null
println(name.orDefault("Guest"))  // "Guest" — no crash
⚡ IBM Q&A
Q: Can extension functions access private members?
No. Extension functions compile to static methods outside the class. They can only access public members. This is a fundamental limitation distinguishing them from actual class members.
Q: Member function vs extension function — same signature — which wins?
The member function always wins. Extension functions are only resolved when no matching member exists. Member functions have higher priority at all times.
Section 04 · Kotlin Core
Null Safety & Types
Kotlin eliminates NullPointerException at compile time. Nothing, Unit, smart casts.
Nullable vs Non-nullable
Definition
Every type in Kotlin is non-nullable by default. To allow null add ?. The compiler then forces you to handle null — preventing NPEs at compile time.
kotlin
val name: String = "John"   // cannot be null
val nick: String? = null   // can be null

nick?.length           // safe call — null if nick is null
nick?.length ?: 0      // Elvis — 0 if nick is null
nick!!.length           // assertion — throws if null. Use sparingly.

if (nick != null) {
    println(nick.length)   // smart cast — no ?. needed
}
nick?.let { println("Nick: $it") }  // runs only when non-null
⚡ IBM Q&A
Q: When would you use !! and why is it risky?
Only when 100% certain it cannot be null at that point. Risky because if wrong, you get KotlinNullPointerException with minimal context — same problem as Java NPE. Always prefer ?: or ?. instead.
Nothing vs Unit
Definition
Unit — Kotlin equivalent of Java void. Returns no meaningful value. Nothing — a type representing a value that never exists. A function that always throws has return type Nothing.
kotlin
fun logEvent(e: String): Unit { println(e) }  // Unit can be omitted

fun fail(msg: String): Nothing { throw IllegalStateException(msg) }

fun getToken(): String =
    prefs.getString("token") ?: fail("Token not found")
    // compiler knows fail() never returns — no type mismatch

sealed class UiState<out T> {
    data class Error(val msg: String) : UiState<Nothing>()  // no T needed
}
⚡ IBM Q&A
Q: Why is Nothing a subtype of every type?
Because Nothing means a value that never exists — it cannot violate any type contract. This is why throw expressions work in any position: val x: String = throw Exception() is valid because throw has type Nothing, a subtype of String.
Section 05 · Kotlin Core
lateinit vs by lazy
Two ways to defer initialization. They solve completely different problems.
lateinit — Manual Deferred Initialization
Definition
lateinit tells the compiler: "I promise I will initialize this before I use it." Used for var properties that cannot be set in the constructor — common in Android because Activity, Fragment, and Service are created by the system, not by you.
Expanding Further
In Android you cannot inject dependencies in a system-created constructor. onCreate() and onViewCreated() are your initialization points. If you access a lateinit property before initializing it, you get UninitializedPropertyAccessException — far more descriptive than a generic NPE, telling you exactly which property was not initialized.
Use Case 1 — ViewBinding
kotlin — ViewBinding with lateinit
class UserFragment : Fragment() {
    // Cannot initialize here — inflater not available at class creation
    private lateinit var binding: FragmentUserBinding

    override fun onCreateView(inflater, container, saved): View {
        binding = FragmentUserBinding.inflate(inflater, container, false)
        return binding.root   // ✅ now initialized
    }

    override fun onViewCreated(view: View, ...) {
        binding.nameTextView.text = "John"  // ✅ safe — already initialized
    }
}
Use Case 2 — Hilt Field Injection
kotlin — Hilt @Inject with lateinit
@AndroidEntryPoint
class MainActivity : AppCompatActivity() {
    // Hilt injects this after the object is created — must be lateinit
    @Inject lateinit var analytics: AnalyticsManager
    @Inject lateinit var navigator: AppNavigator

    override fun onCreate(saved: Bundle?) {
        super.onCreate(saved)
        analytics.logScreenView("main")  // ✅ Hilt has injected by now
    }
}
Use Case 3 — RecyclerView Adapter
kotlin — Adapter with lateinit
class UserFragment : Fragment() {
    private lateinit var adapter: UserAdapter  // adapter changes as data changes

    override fun onViewCreated(view: View, ...) {
        adapter = UserAdapter { user -> viewModel.onUserSelected(user) }
        binding.recyclerView.adapter = adapter

        // Safe check before accessing
        if (::adapter.isInitialized) {
            adapter.submitList(emptyList())
        }
    }
}
⚠️ lateinit restrictions: Only var (not val). Cannot be nullable types (String?). Cannot be primitives (Int, Boolean, Float) — use nullable (Int?) instead. Always initialize before first access.
by lazy — Automatic Deferred Initialization
Definition
by lazy computes the value on first access and caches it forever. The block runs exactly once. Used for val (immutable) properties that are expensive to create or depend on other initialized properties.
Expanding Further — Internal Working
by lazy uses the Lazy<T> interface internally. Default mode is LazyThreadSafetyMode.SYNCHRONIZED — a lock ensures only one thread initializes it. After initialization, subsequent accesses skip the lock. The block stores either an uninitialized sentinel or the cached result.
Use Case 1 — ViewModel via viewModels()
kotlin
class UserFragment : Fragment() {
    // viewModels() returns a lazy delegate — ViewModel created on first access
    private val viewModel: UserViewModel by viewModels()
    // If Fragment recreates, same ViewModel instance returned from ViewModelStore
}
Use Case 2 — Room Database in Application
kotlin
class MyApp : Application() {
    // Room is expensive — create once, share everywhere
    val database: AppDatabase by lazy {
        Room.databaseBuilder(this, AppDatabase::class.java, "app_db")
            .fallbackToDestructiveMigration()
            .build()
        // Created only on first access, cached for entire app lifetime
    }
}
Use Case 3 — Expensive Computation (Regex)
kotlin
class InputValidator {
    // Regex compilation is expensive — do it once
    private val emailRegex: Regex by lazy {
        Regex("^[A-Za-z0-9+_.-]+@[A-Za-z0-9.-]+\$")
    }
    // Regex compiled on first call to isValidEmail(), then reused
    fun isValidEmail(email: String) = emailRegex.matches(email)
}

// Thread safety modes
val safe by lazy(LazyThreadSafetyMode.SYNCHRONIZED) { compute() }  // default
val fast by lazy(LazyThreadSafetyMode.NONE) { compute() }           // no lock — single thread

⚡ IBM Q&A
Q: What exception is thrown when you access an uninitialized lateinit property?
UninitializedPropertyAccessException. It is more helpful than NPE because it tells you exactly which property was not initialized before access. Use ::field.isInitialized to guard access when unsure.
Q: Why can't you use lateinit with primitives like Int?
lateinit uses null internally as the "uninitialized" sentinel. Kotlin primitives (Int, Boolean, Float) compile to JVM primitives which cannot hold null — so there is no way to mark them uninitialized. Use nullable Int? instead.
Q: Can by lazy be re-initialized?
No. Once initialized, the cached value is returned forever. The block never runs again. If you need a property that can be reset, use lateinit var or a regular var with manual management.
Q: Is by lazy always thread safe?
By default yes — it uses LazyThreadSafetyMode.SYNCHRONIZED which locks on the object during initialization. For single-threaded scenarios you can use LazyThreadSafetyMode.NONE for better performance by skipping the lock overhead.

Scope Functions
5 functions — let, run, with, apply, also. Each explained with Definition → Purpose → Syntax → Android Example → IBM Q.
Definition
Scope functions execute a block of code in the context of an object. They do not add functionality — they make code readable by creating a temporary scope where you can work with an object without repeating its name. Kotlin has exactly 5 scope functions.
Memory trick: apply / also → return the object. let / run / with → return the lambda result. apply / run / with → use this. let / also → use it.

1. let
Definition
let — refers to the object as it. Returns the lambda result (last line). Used primarily for null safety checks and transforming an object into something else.
Purpose / When to Use
• Execute a block only when the object is non-null
• Transform an object into a different type
• Introduce a temporary variable in a local scope without polluting the outer scope
• Chain operations on an object
Syntax
val result = object?.let { it -> /* block */ lastLineReturned }
kotlin — let basic example
val email: String? = getEmailFromPrefs()

// Null safety — block runs ONLY if email is non-null
email?.let { validEmail ->
    viewModel.login(validEmail)
} ?: showError("Email not found")

// Transformation — let returns the last line
val displayName: String = user?.let {
    "${it.name} (${it.email})"  // this String is returned from let
} ?: "Guest"
kotlin — let Android example
// ViewModel — handle nullable API response safely
fun processResponse(response: ApiResponse<User>?) {
    response?.let { res ->
        if (res.isSuccessful())
            _uiState.value = UiState.Success(res.body)
        else
            _uiState.value = UiState.Error(res.errorMessage)
    } ?: run {
        _uiState.value = UiState.Error("Response was null")
    }
}

// Composable — show user data only when non-null
viewModel.user.collectAsStateWithLifecycle().value?.let { user ->
    Text(text = user.name)
    Text(text = user.email)
}
⚡ IBM Q&A
Q: What does ?.let do differently from if (x != null)?
?.let is an expression — it returns a value and can be chained. if (x != null) is a statement. let also creates a local scope so the safe non-null object is available as it without being in the outer scope. It reads left-to-right and is composable.
Q: What does let return?
The last expression in the lambda. If no meaningful last line, it returns Unit.
2. run
Definition
run — refers to the object as this. Returns the lambda result. Also has a standalone (non-extension) form — runs a block without any receiver and returns its result.
Purpose / When to Use
• Compute a result using multiple properties of an object (access without repeating the object name)
• Group related initialization code that produces a return value
• Replace a block of code that needs to return a computed result
kotlin — run basic example
// Access multiple properties without repeating object name
val isFormValid = user.run {
    name.isNotEmpty() && email.contains("@") && age >= 18
    // this.name, this.email, this.age — this = user
}

// Non-extension form — standalone block returning a value
val retrofit = run {
    val logging = HttpLoggingInterceptor()
    val okHttp = OkHttpClient.Builder().addInterceptor(logging).build()
    Retrofit.Builder().baseUrl(BASE_URL).client(okHttp).build()
}  // Retrofit returned
kotlin — run Android example
// ViewModel — build a UiState from user object cleanly
val state: UiState = user?.run {
    UiState.Success(
        displayName = "$name ($email)",
        isVerified = email.contains("@gmail"),
        avatarUrl = profileImageUrl
    )
} ?: UiState.Error("No user data")
⚡ IBM Q&A
Q: Difference between let and run?
Both return the lambda result. let uses it — good for null checks and renaming. run uses this — good when accessing multiple properties directly without any prefix. For nullable objects both support ?. but let is preferred for null checks.
Q: What is the non-extension form of run used for?
Running a block of code that needs to return a value and uses temporary variables you don't want in the outer scope. It groups related setup code cleanly — like building a Retrofit or OkHttp instance from multiple steps.
3. with
Definition
with — NOT an extension function. The object is passed as a parameter. Refers to it as this. Returns the lambda result. Best for calling multiple methods or setting multiple properties on a guaranteed non-null object.
Purpose / When to Use
• Call multiple methods on the same non-null object without repeating its name
• Read multiple values from SharedPreferences
• Set multiple properties on ViewBinding — the most common Android use case
• NOT suitable for nullable objects — use ?.run {} instead
kotlin — with basic example
val person = Person("Rahul", 28, "Delhi")

// Without with — repeating person.
println(person.name); println(person.age); println(person.city)

// With with — clean, this = person
with(person) {
    println(name)   // this.name
    println(age)
    println(city)
}
kotlin — with Android example
// ViewBinding — set multiple views without repeating binding.
with(binding) {
    nameTextView.text = user.name
    emailTextView.text = user.email
    avatarImageView.load(user.avatarUrl)
    progressBar.visibility = View.GONE
    submitButton.isEnabled = true
    retryButton.visibility = View.GONE
}

// SharedPreferences — multiple reads returning a data object
val session = with(getSharedPreferences("prefs", MODE_PRIVATE)) {
    Session(
        token  = getString("token", "") ?: "",
        userId = getString("userId", "") ?: "",
        expiry = getLong("expiry", 0)
    )  // Session object returned from with
}
⚡ IBM Q&A
Q: with vs run — difference?
Both use this and return the lambda result. Difference is syntax — run is called ON the object (object.run {}), with takes the object as a parameter (with(object) {}). For nullable objects use object?.run {} — with does not support safe call syntax.
Q: Can you use with on a nullable object?
Not safely. with(nullableObject) would throw NPE if null. Use nullableObject?.run {} instead for nullable scenarios.
4. apply
Definition
apply — refers to the object as this. Returns the object itself — NOT the last line. Designed for object configuration — you set properties and get the configured object back.
Purpose / When to Use
• Configure an object right after creating it — builder pattern style
• Set multiple properties on the same object
• Intent setup, AlertDialog setup, Retrofit/OkHttp builder config
• When you want the object returned so you can chain further or assign it
kotlin — apply basic example
data class Address(var street: String = "", var city: String = "")

// Without apply
val addr1 = Address()
addr1.street = "MG Road"
addr1.city = "Bangalore"

// With apply — cleaner, returns configured Address object
val addr2 = Address().apply {
    street = "MG Road"   // this.street
    city = "Bangalore"   // this.city
}
kotlin — apply Android example
// Intent setup
val intent = Intent(this, DetailActivity::class.java).apply {
    putExtra("userId", user.id)
    putExtra("userName", user.name)
    flags = Intent.FLAG_ACTIVITY_NEW_TASK
}
startActivity(intent)

// Retrofit + OkHttp builder
val okHttp = OkHttpClient.Builder().apply {
    addInterceptor(HttpLoggingInterceptor().apply { level = BODY })
    connectTimeout(30, TimeUnit.SECONDS)
    readTimeout(30, TimeUnit.SECONDS)
}.build()  // apply returns Builder, then .build() called

val retrofit = Retrofit.Builder().apply {
    baseUrl("https://api.example.com/")
    client(okHttp)
    addConverterFactory(GsonConverterFactory.create())
}.build()
⚡ IBM Q&A
Q: What does apply return?
apply always returns the object it was called on — NOT the last line of the lambda. This is what makes it ideal for configuration — you set up properties and get the configured object back for assignment or chaining.
Q: apply vs also — both return the object. Difference?
apply uses this — access/set the object's own properties directly. Designed for configuration. also uses it — the object is a parameter. Designed for side effects like logging or analytics. Semantically: apply configures the object's state, also observes it without changing it.
5. also
Definition
also — refers to the object as it. Returns the object itself. Used for side effects — things you do with the object that do not configure or transform it, like logging, analytics tracking, or validation.
Purpose / When to Use
• Log or debug an object mid-chain without breaking the chain
• Track analytics events when an object is created or fetched
• Validate an object without modifying it
• Any side effect where you want the original object flowing through unchanged
Think of it as
"Also do this thing while I have this object — but give me the original object back."
kotlin — also basic example
// Log intermediate states in a chain — also does not break the chain
val result = listOf(1, 2, 3, 4, 5)
    .also { println("Original: $it") }
    .filter { it > 2 }
    .also { println("After filter: $it") }
    .map { it * 10 }
    .also { println("After map: $it") }
// Output: Original:[1,2,3,4,5] → After filter:[3,4,5] → After map:[30,40,50]
kotlin — also Android example
// Repository — log, cache, and track BEFORE returning user
suspend fun getUser(id: String): User {
    return apiService.getUser(id)
        .also { user ->
            // Side effects — none of these transform the user object
            logger.d("Fetched user: ${user.name}")
            userDao.insert(user)           // cache locally
            analytics.log("user_fetched")  // track event
        }  // user object returned unchanged
}
⚡ IBM Q&A
Q: When would you prefer also over let?
When you do not want to transform the object — only observe or log it. let returns the lambda result (transformation). also returns the object unchanged (pass-through). If the object must continue flowing through a chain unchanged, also is the right choice.
Q: What does also return?
always returns the object it was called on, NOT the last line. This makes it perfect for mid-chain operations — the chain continues with the same original object.
Section 07 · Kotlin Core
Higher-Order Functions & Lambdas
inline, noinline, crossinline, reified — the advanced function concepts IBM tests at senior level.
Lambda & Higher-Order Function
Definition
A lambda is an anonymous function stored in a variable or passed as an argument. A higher-order function takes a function as a parameter or returns one. This is the foundation of Kotlin's functional style.
kotlin
val multiply: (Int, Int) -> Int = { x, y -> x * y }

fun operate(a: Int, b: Int, op: (Int, Int) -> Int): Int = op(a, b)

operate(10, 5) { x, y -> x + y }   // trailing lambda syntax — 15
operate(10, 5, multiply)            // passing lambda variable — 50
val double: (Int) -> Int = { it * 2 }  // it = default single param name
inline performance
Definition
inline functions copy the lambda bytecode directly into the call site instead of creating an anonymous class object. Eliminates object allocation overhead for lambdas — important in hot paths like loops and collection operations.
Expanding Further
Without inline, every lambda creates an anonymous object at runtime — GC pressure in hot paths. With inline, the compiler pastes the lambda body at every call site — zero object allocation. Downside: large inline functions increase bytecode size at every usage.
kotlin
// inline — lambda bytecode pasted at call site, no object created
inline fun measureTime(block: () -> Unit) {
    val start = System.currentTimeMillis()
    block()
    println("${System.currentTimeMillis() - start}ms")
}

// noinline — exclude one lambda so it can be stored as an object
inline fun register(
    onSuccess: () -> Unit,
    noinline onError: () -> Unit   // NOT inlined — can be stored/passed
) {
    onSuccess()
    saveCallback(onError)           // storing requires noinline
}

// crossinline — allow inlining but prevent non-local returns
inline fun runOnBackground(crossinline block: () -> Unit) {
    Thread { block() }.start()
    // crossinline: cannot write "return" inside block here
}
⚡ IBM Q&A
Q: Difference between noinline and crossinline?
noinline — marks a lambda NOT to be inlined so it can be stored as an object or passed to another function. crossinline — allows inlining but disallows non-local returns from the lambda. Use crossinline when the lambda is called inside a different execution context (Thread, callback) where returning from the outer function would be invalid.
Q: When should you NOT use inline?
For large functions — inlining a 50-line function at every call site bloats bytecode significantly. Use inline for small higher-order functions called frequently, like collection operators or timing utilities.
reified inline only
Definition
reified retains the actual type at runtime, bypassing type erasure. Can ONLY be used with inline functions — inlining pastes the actual type at each call site so the compiler knows T at runtime.
Expanding Further — Why Type Erasure is a Problem
Normally generics are erased at runtime — List<String> becomes just List at bytecode level. You cannot write T::class.java in a regular generic function because T is unknown. reified with inline solves this by substituting the real type at every call site during compilation.
kotlin
// Without reified — compile error, T is erased
fun <T> fromJson(json: String): T =
    gson.fromJson(json, T::class.java)  // ❌ T::class not allowed

// With reified — T is known at runtime at each call site
inline fun <reified T> fromJson(json: String): T =
    gson.fromJson(json, T::class.java)  // ✅ works

val user = fromJson<User>(jsonString)  // clean — no Class param needed

// Android — start Activity without passing .class
inline fun <reified T : Activity> Context.startActivity() {
    startActivity(Intent(this, T::class.java))
}
startActivity<DetailActivity>()  // no .class parameter needed
⚡ IBM Q&A
Q: Why does reified only work with inline?
Because inline copies the function body at every call site. The compiler knows the actual type T at each call site and substitutes it directly into the pasted code. Without inline, the function is a single bytecode method where T is erased — there is no call site to substitute into.
Section 08 · Kotlin Core
Collections & Operators
map, filter, flatMap, reduce, fold, groupBy, partition — most asked in coding rounds.
Core Operators
Definition
Kotlin collections have built-in functional operators that transform, filter, or reduce data. Each returns a new collection — the original is not modified (immutable operation).
kotlin
data class User(val name: String, val age: Int, val isPremium: Boolean)
val users = listOf(User("Alice",30,true), User("Bob",17,false), User("Charlie",25,true))

// MAP — transform each element, returns same-size list
users.map { it.name }                  // [Alice, Bob, Charlie]
users.map { it.name.uppercase() }     // [ALICE, BOB, CHARLIE]

// FILTER — keep matching elements
users.filter { it.age >= 18 }         // [Alice, Charlie]
users.filter { it.isPremium }          // [Alice, Charlie]

// FLATMAP — map then flatten (list of lists → flat list)
listOf(listOf("a","b"), listOf("c","d")).flatMap { it }  // [a,b,c,d]

// REDUCE — combine, no initial value (throws on empty list)
listOf(1,2,3).reduce { acc, n -> acc + n }  // 6

// FOLD — combine WITH initial value (safe on empty list)
listOf(1,2,3).fold(100) { acc, n -> acc + n }  // 106

// GROUPBY — Map<Key, List<T>>
users.groupBy { it.isPremium }  // {true=[Alice,Charlie], false=[Bob]}

// PARTITION — Pair<List, List>
val (adults, minors) = users.partition { it.age >= 18 }

// ANY, ALL, NONE, COUNT
users.any  { it.age < 18 }    // true
users.all  { it.age >= 18 }   // false
users.none { it.age > 60 }    // true
users.count{ it.isPremium }    // 2

// FIRST vs FIRSTORNULL vs FIND
users.first       { it.age > 20 }  // throws NoSuchElementException if not found
users.firstOrNull { it.age > 50 }  // null — safe
users.find        { it.name == "Bob" }  // same as firstOrNull
asSequence() — Lazy Evaluation
Definition
asSequence() converts a collection to a lazy sequence. Instead of creating a full intermediate list at each step, it processes one element at a time through the entire pipeline — critical performance optimization for large collections.
kotlin
// WITHOUT sequence — 2 full lists created in memory
(1..1_000_000)
    .filter { it % 2 == 0 }   // list of 500k elements
    .map    { it * 3 }            // another 500k list
    .take   (5)                    // takes 5 from 500k

// WITH sequence — 1 element at a time, stops after 5 found
(1..1_000_000).asSequence()
    .filter { it % 2 == 0 }   // lazy — no list
    .map    { it * 3 }            // lazy — no list
    .take   (5)                    // stops immediately after 5!
    .toList()                      // terminal op — triggers execution
⚡ IBM Q&A
Q: Difference between reduce and fold?
reduce has no initial value — uses first element as accumulator. Throws NoSuchElementException on empty list. fold requires an initial value — safe on empty collections. Prefer fold for safety unless the list is guaranteed non-empty.
Q: When should you NOT use asSequence?
For small collections. Sequences have overhead from lazy wrapper objects and lambda call indirection. The crossover where sequences outperform eager evaluation is roughly 1000+ elements with multiple chained operators. For small lists, regular operators are faster.
Section 09 · Kotlin Core
Delegation
Delegate property or class behavior to another object using the by keyword.
Delegates.observable — React to Property Changes
Definition
Delegates.observable calls a callback every time the property value changes, providing the property name, old value, and new value. Useful for reacting to state changes without LiveData or StateFlow.
kotlin
class UserPreferences {
    var theme: String by Delegates.observable("light") { prop, old, new ->
        println("${prop.name} changed: $old -> $new")
        applyTheme(new)
    }
}
val prefs = UserPreferences()
prefs.theme = "dark"    // theme changed: light -> dark
prefs.theme = "system"  // theme changed: dark -> system
Class Delegation — by keyword
Definition
Class delegation using by forwards all interface method calls to another object automatically. You only override the methods you want to change — everything else is delegated with zero boilerplate. Implements the Decorator pattern cleanly.
kotlin
interface UserRepository {
    suspend fun getUser(id: String): User
    suspend fun saveUser(user: User)
    suspend fun deleteUser(id: String)
}

// Logging decorator — only override getUser, rest auto-delegated
class LoggingUserRepository(
    private val delegate: UserRepository
) : UserRepository by delegate {    // ALL methods forwarded to delegate

    override suspend fun getUser(id: String): User {
        println("Getting user: $id")       // add logging
        return delegate.getUser(id)       // delegate the real call
    }
    // saveUser() and deleteUser() auto-forwarded — no code needed
}
by viewModels() — Behind the Scenes
Definition
by viewModels() is an Android KTX property delegate that lazily retrieves a ViewModel from ViewModelProvider on first access and caches it — all through Kotlin's delegation mechanism.
kotlin
// What you write
val viewModel: UserViewModel by viewModels()

// What Kotlin generates behind the scenes
private val _vm_delegate = viewModels<UserViewModel>()
val viewModel: UserViewModel
    get() = _vm_delegate.getValue(this, ::viewModel)

// viewModels() returns Lazy<VM> which internally calls:
// ViewModelProvider(this)[UserViewModel::class.java]
⚡ IBM Q&A
Q: Difference between by viewModels() and ViewModelProvider(this).get()?
They return the same ViewModel instance. by viewModels() is lazy — only calls ViewModelProvider on first property access. It is concise and integrates with Kotlin delegation. Internally they perform the same ViewModelStore lookup.
Section 10 · Kotlin Core
Generics
Covariance (out), Contravariance (in), Star Projection, Type Erasure.
out T — Covariance (Producer)
Definition
out T — the class can only produce/return T. Cannot accept T as a parameter. Allows a subtype to be used where a supertype is expected (covariant).
kotlin
interface ApiResponse<out T> {
    fun getData(): T       // ✅ can produce/return T
    // fun set(item: T) {} ❌ cannot consume T as parameter
}

val userResponse: ApiResponse<User> = fetchResponse()
val anyResponse: ApiResponse<Any> = userResponse  // ✅ covariant — User IS-A Any

// Kotlin List is covariant — List<String> can be used as List<Any>
val strings: List<String> = listOf("a", "b")
val anys: List<Any> = strings  // ✅ works because List is declared out T
in T — Contravariance (Consumer)
Definition
in T — the class can only consume/accept T. Cannot produce/return T. Allows a supertype to be used where a subtype is expected (contravariant).
kotlin
interface EventLogger<in T> {
    fun log(event: T)    // ✅ can consume T
    // fun get(): T {}   ❌ cannot produce T
}

val anyLogger: EventLogger<Any> = createLogger()
val clickLogger: EventLogger<ClickEvent> = anyLogger
// ✅ Any logger can handle ClickEvent — contravariance
⚡ IBM Q&A
Q: Simple trick to remember in vs out?
Producer out — the class gives you T, you read from it. Consumer in — the class takes T from you, you write into it. Kotlin List is out (read-only). MutableList is invariant (no in/out) because it can both read and write.
Q: What is star projection?
Box<*> means you don't know or don't care about the type. You can read from it as Any? but cannot write to it. Used when passing a generic object around without needing its specific type parameter.
Section 11 · Architecture
SOLID Principles
All 5 principles with real Kotlin + Android codebase examples. No Shape or Rectangle classes.
S
Single Responsibility Principle
A class should have only ONE reason to change.
Definition
Every class, function, or module should do one thing only. If a class has multiple responsibilities, changes in one area can break unrelated functionality. Split it into focused, single-purpose classes.
❌ BAD — LoginViewModel doing 5 different jobs 
class LoginViewModel : ViewModel() {
    fun login(email: String, pass: String) {
        // 1. Validating input
        if (!email.contains("@")) return
        // 2. Making API call directly
        val resp = Retrofit.create(ApiService::class.java).login(email, pass)
        // 3. Saving token to SharedPreferences
        prefs.edit().putString("token", resp.token).apply()
        // 4. Logging to analytics
        Firebase.logEvent("login_success")
        // 5. Formatting display name
        _displayName.value = email.substringBefore("@").replaceFirstChar { it.uppercase() }
    }
}
✅ GOOD — Each class has one job, one reason to change 
// 1. Only validates — changes only if validation rules change
class LoginValidator {
    fun validate(email: String, pass: String): ValidationResult {
        val emailOk = email.contains("@") && email.contains(".")
        val passOk  = pass.length >= 8
        return ValidationResult(emailOk && passOk)
    }
}

// 2. Only handles auth API — changes only if auth endpoint changes
interface AuthRepository {
    suspend fun login(email: String, pass: String): AuthToken
}

// 3. Only stores tokens — changes only if storage mechanism changes
class TokenManager @Inject constructor(private val prefs: SharedPreferences) {
    fun saveToken(token: String) = prefs.edit().putString("token", token).apply()
}

// 4. Only tracks events — changes only if analytics provider changes
class AnalyticsManager @Inject constructor() {
    fun logLogin() = Firebase.logEvent("login_success")
}

// 5. ViewModel — ORCHESTRATES only, does NOT do the actual work
@HiltViewModel
class LoginViewModel @Inject constructor(
    private val validator: LoginValidator,
    private val authRepo:  AuthRepository,
    private val tokenMgr:  TokenManager,
    private val analytics: AnalyticsManager
) : ViewModel() {
    fun login(email: String, pass: String) {
        if (!validator.validate(email, pass).isValid) return
        viewModelScope.launch {
            val token = authRepo.login(email, pass)
            tokenMgr.saveToken(token.value)
            analytics.logLogin()
        }
    }
}
⚡ IBM Q&A
Q: How does SRP apply to MVVM?
Each layer has one responsibility — View shows UI (reason to change: design changes), ViewModel holds UI state (reason to change: business logic changes), Repository fetches data (reason to change: data source changes). If ViewModel is making network calls directly, it is violating SRP.
O
Open/Closed Principle
Open for extension, closed for modification.
Definition
You should be able to add new behavior without modifying existing working code. Extend by adding new classes, not by editing old ones. If adding a new feature requires modifying existing tested code — OCP is being violated.
❌ BAD — Adding a new push channel requires modifying existing class 
class NotificationManager {
    fun send(type: String, msg: String) {
        when (type) {
            "FCM"   -> sendFcm(msg)
            "SMS"   -> sendSms(msg)
            // Adding WhatsApp = modifying this class = BAD
            "WA"    -> sendWhatsApp(msg)
        }
    }
}
✅ GOOD — New channel = new class, zero modification to existing code 
interface NotificationChannel { fun send(msg: String) }

class FcmChannel : NotificationChannel {
    override fun send(msg: String) { /* FCM push logic */ }
}
class SmsChannel : NotificationChannel {
    override fun send(msg: String) { /* SMS logic */ }
}
// Adding WhatsApp = just a new class, existing code untouched
class WhatsAppChannel : NotificationChannel {
    override fun send(msg: String) { /* WA logic */ }
}

// Manager is closed for modification — open for extension via Hilt set binding
class NotificationManager @Inject constructor(
    private val channels: Set<NotificationChannel>
) {
    fun broadcast(msg: String) = channels.forEach { it.send(msg) }
}
⚡ IBM Q&A
Q: How do you apply OCP in an Android project practically?
Use interfaces and dependency injection. When you inject a Set or List of implementations via Hilt, adding a new implementation is purely additive — you add the class and a Hilt binding. The existing manager class, tests, and all other code remain completely unchanged.
L
Liskov Substitution Principle
Subclass must be substitutable for parent without breaking behavior.
Definition
If your code works with a parent type, it must still work correctly when a subclass is substituted. Never override a method in a way that violates the parent's behavioral contract — throwing UnsupportedOperationException is the classic violation.
❌ BAD — ReadOnlyRepository breaks the Repository contract 
open class UserRepository {
    open fun save(user: User)   { /* saves to DB */ }
    open fun delete(id: String) { /* deletes from DB */ }
}

class ReadOnlyRepository : UserRepository() {
    override fun save(user: User) {
        throw UnsupportedOperationException("Read-only!")  // ❌ breaks contract
    }
    override fun delete(id: String) {
        throw UnsupportedOperationException("Read-only!")  // ❌ breaks contract
    }
}
// Any code using UserRepository will crash if ReadOnlyRepository is substituted
✅ GOOD — Honest contracts through interface segregation 
interface ReadableUserRepository {
    suspend fun getUser(id: String): User
}
interface WritableUserRepository : ReadableUserRepository {
    suspend fun saveUser(user: User)
    suspend fun deleteUser(id: String)
}

// Cache — only read — honest contract, no throws
class CacheUserRepository : ReadableUserRepository {
    override suspend fun getUser(id: String): User { /* from cache */ }
}

// Room DB — full read + write — honest contract
class RoomUserRepository : WritableUserRepository {
    override suspend fun getUser(id: String): User  { /* from Room */ }
    override suspend fun saveUser(user: User)       { /* to Room */ }
    override suspend fun deleteUser(id: String)     { /* from Room */ }
}
Android rule: Always call super.onSaveInstanceState() when overriding — skipping it breaks the parent Activity's state-saving contract and causes state loss on rotation.
I
Interface Segregation Principle
Don't force classes to implement methods they don't use.
Definition
Split large fat interfaces into smaller focused ones. Each class should only implement the interface methods it actually needs. Forcing a class to implement methods it doesn't use leads to empty stubs or UnsupportedOperationException.
❌ BAD — Fat listener forces Fragment to implement all methods 
interface UserListListener {
    fun onUserClick(user: User)
    fun onUserLongClick(user: User)
    fun onSwipeDelete(user: User)
    fun onSwipeArchive(user: User)
    fun onHeaderClick()
}

// SearchFragment only needs click — forced to write 4 empty stubs
class SearchFragment : Fragment(), UserListListener {
    override fun onUserClick(user: User) { navigateToDetail(user) }
    override fun onUserLongClick(user: User) {}  // ❌ empty stub
    override fun onSwipeDelete(user: User) {}   // ❌ empty stub
    override fun onSwipeArchive(user: User) {}  // ❌ empty stub
    override fun onHeaderClick() {}              // ❌ empty stub
}
✅ GOOD — Focused interfaces, each Fragment implements only what it needs 
interface OnUserClickListener     { fun onUserClick(user: User) }
interface OnUserLongClickListener { fun onUserLongClick(user: User) }
interface OnSwipeListener {
    fun onSwipeDelete(user: User)
    fun onSwipeArchive(user: User)
}

// SearchFragment — only click needed
class SearchFragment : Fragment(), OnUserClickListener {
    override fun onUserClick(user: User) { navigateToDetail(user) }
}

// InboxFragment — needs click + swipe
class InboxFragment : Fragment(), OnUserClickListener, OnSwipeListener {
    override fun onUserClick(user: User)    { openChat(user) }
    override fun onSwipeDelete(user: User)  { viewModel.delete(user) }
    override fun onSwipeArchive(user: User) { viewModel.archive(user) }
}
D
Dependency Inversion Principle
Depend on abstractions, not concretions.
Definition
High-level modules (ViewModel) should NOT depend on low-level modules (Retrofit, Room). Both should depend on abstractions (interfaces). This is what makes Dependency Injection possible and tests free of real network calls.
❌ BAD — ViewModel directly coupled to Retrofit 
class UserViewModel : ViewModel() {
    // Directly creating concrete dependency — cannot mock in tests
    private val api = Retrofit.Builder()
        .baseUrl("https://api.example.com/")
        .build()
        .create(ApiService::class.java)

    fun getUser(id: String) = viewModelScope.launch {
        val user = api.getUser(id)  // real network call in every test!
    }
}
✅ GOOD — ViewModel depends on interface, not Retrofit 
// Abstraction — ViewModel knows only this contract
interface UserRepository {
    suspend fun getUser(id: String): Result<User>
}

// Low-level: Retrofit implementation — detail hidden from ViewModel
class UserRepositoryImpl @Inject constructor(
    private val api: ApiService
) : UserRepository {
    override suspend fun getUser(id: String) = runCatching { api.getUser(id) }
}

// High-level: ViewModel depends on abstraction only
@HiltViewModel
class UserViewModel @Inject constructor(
    private val repo: UserRepository  // interface — not Retrofit
) : ViewModel() {
    fun getUser(id: String) = viewModelScope.launch {
        repo.getUser(id)  // no idea if it's Retrofit, Room, or a Fake
    }
}

// Test — swap real impl with fake, zero network calls
class FakeUserRepository : UserRepository {
    override suspend fun getUser(id: String) =
        Result.success(User("1", "Test User", "test@test.com"))
}
⚡ IBM Q&A
Q: How does Hilt implement DIP?
Hilt's @Binds or @Provides in a Module maps the interface (UserRepository) to the concrete implementation (UserRepositoryImpl). ViewModel only declares @Inject with the interface type — Hilt injects the right implementation at runtime. Switching from Retrofit to GraphQL means only changing the Module — ViewModel and all tests are completely untouched.
Q: Is Dependency Injection the same as Dependency Inversion Principle?
No — they are related but different. DIP is the principle: depend on abstractions. DI is the technique used to achieve it — passing dependencies from outside instead of creating them internally. You can have DI without DIP (injecting a concrete class) but DIP encourages DI through interfaces.
